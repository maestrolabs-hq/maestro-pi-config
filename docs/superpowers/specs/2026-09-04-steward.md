# The steward and its correction journal

Status: proposed design, not implemented. Supersedes Part 2 of
`docs/superpowers/specs/2026-09-03-agent-orchestration-and-steward.md`, which
recorded the steward as a sketch before any model had been measured. Part 1 of
that document, the routing matrix, is untouched.

The steward is a local model-driven clerk. It records each orchestration round
to a ledger and raises what needs the operator's attention. That is the whole
job.

Revised after an adversarial review found eight blockers, three of which
reversed decisions this document had locked. What changed, and why, is stated
at each site rather than collected here; the largest is that the steward's
models are now **resident**, because the on-demand arrangement this document
previously settled on would have evicted the 27B model the operator works
with. Every claim below about pi's runtime or the router was re-checked
against the installed code, and file references are given so the next reader
can re-check them too.

## What the bench settled, and what it did not

Measured this session against the two candidate models on disk, both declared
in the router catalog of the `maestro-llamacpp` repository.

| | `qwen3-06b` (Q8, ~640 MB) | `qwen3-4b` (Q4) |
| --- | --- | --- |
| Load | ~1 s | ~6 s |
| Held while loaded | ~1 GB | ~7 GB at 32k context |
| Answer to a steward prompt | ~4 s | ~4 s |
| Answer with a `json_schema` grammar | ~0.75 s | ~4 s |
| Valid JSON without a grammar | yes | yes |
| Straightforward round | correct | correct |
| Round with competing priorities | **wrong** | correct |

Two findings carry this design.

**Form is free.** Both models emitted valid operations with no grammar at all,
and with a `json_schema` grammar the output is valid by construction. So a
schema is worth using -- it makes a class of failure impossible, and on the
0.6B it is also five times faster -- but nothing in this design may be built on
the belief that form was the hard part.

**Priority arbitration is where the small model fails.** Given a round holding
a security blocker beside routine progress, the 0.6B buried the blocker in a
`note_decision` and raised the routine item instead. The 4B ordered both rounds
correctly. The failure was not malformed, not refused, and not obviously wrong
from the output alone. It was a wrong judgement in valid clothes.

What the bench could not settle is which model to use in general. Two prompts
are two data points. That is what the correction journal exists to fix.

## Purpose

Round-by-round clerical upkeep, which today costs orchestrator turns and
context that should go to the work.

Each round the steward answers two questions:

1. What happened, in a form that can be read back later.
2. Is there anything here a human has to look at.

## Non-goals

- **Not the orchestrator.** It never dispatches, never re-dispatches, never
  chooses a model for anything but itself.
- **No engineering decisions.** It does not decide that a task exists, that a
  design is right, or that a failure is acceptable. It records and it raises.
- **Never blocking.** A steward that cannot reach its model, or that answers
  slowly, costs the round nothing. Pi awaits extension handlers one after
  another and releases the session's idle wait only when the last of them
  returns, so this is a claim about how the handler is written and not a hope:
  see "Nothing waits for the steward".
- **Never competing for memory.** A steward call never evicts, swaps, delays
  or refuses a model the operator is working with. This constraint outranks
  every other consideration here, and the router integration is built around
  it rather than checked against it afterwards.
- **No write path beyond its own two files.** No tools, no shell, no arbitrary
  paths. The model proposes; deterministic code writes.
- **No training.** A fine-tune becomes a conversation only if the journal shows
  systematic error after real use.

## The operation vocabulary

Four operations, closed set.

| Operation | Meaning |
| --- | --- |
| `{"check_task": <int>}` | Mark task *n* in the current state file done. |
| `{"note_decision": "<text>"}` | Record something the round settled. |
| `{"flag_user": "<text>"}` | Raise one thing that needs a human. |
| `{"noop": true}` | The round changed nothing worth recording. |

`flag_user` is the only operation with a cost when it is wrong, in both
directions, so its semantics are narrow: **a risk, a blocker, something broken,
or an unresolved question.** Not progress. Not a summary. Not a plan. If a
competent operator reading it would not have to do anything, it is a
`note_decision`.

The earlier sketch used `add`, `complete`, `block`, `note`, `noop`. Two of
those are gone deliberately. `add` let the steward invent work, which is an
engineering decision and therefore not its to make -- a round that discovers
new work says so in a `note_decision` and the orchestrator decides whether it
is a task. `block` was `flag_user` under another name, and two words for one
idea is how a vocabulary rots.

### The schema

Sent as `response_format` on every call, so the router constrains decoding and
the reply cannot be malformed.

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["operations"],
  "properties": {
    "operations": {
      "type": "array",
      "minItems": 1,
      "maxItems": 8,
      "items": {
        "oneOf": [
          {
            "type": "object",
            "additionalProperties": false,
            "required": ["check_task"],
            "properties": { "check_task": { "type": "integer", "minimum": 1 } }
          },
          {
            "type": "object",
            "additionalProperties": false,
            "required": ["note_decision"],
            "properties": { "note_decision": { "type": "string", "maxLength": 280 } }
          },
          {
            "type": "object",
            "additionalProperties": false,
            "required": ["flag_user"],
            "properties": { "flag_user": { "type": "string", "maxLength": 280 } }
          },
          {
            "type": "object",
            "additionalProperties": false,
            "required": ["noop"],
            "properties": { "noop": { "type": "boolean", "const": true } }
          }
        ]
      }
    }
  }
}
```

The grammar guarantees shape, never sense. A deterministic validator sits
between the reply and the disk and refuses what the schema cannot express: a
`check_task` index outside the current list, an index already checked, a
`noop` arriving beside other operations. A refusal is journalled as a rejected
proposal, which is exactly the signal the journal exists to collect.

## The correction journal

The centrepiece. One line at a time, it turns a question nobody can answer from
a bench into a question that answers itself: **is the 0.6B good enough.**

### Storage

An append-only JSONL file per session, with that session's task state beside
it:

```text
<pi agent dir>/steward/<session id>/journal.jsonl
<pi agent dir>/steward/<session id>/state.json
```

The root is derived at run time from `PI_AGENT_DIR`, falling back to the pi
directory under the home directory, the same derivation `src/manifest.rs:109`
already uses. Nothing here names a machine.

**Decided: a directory per session, not one per machine.** This was one file
per machine, and it was wrong. `PI_AGENT_DIR` resolves to a single directory,
and this estate runs many panes at once, each of them a pi session that loads
the same extension. One shared `state.json` would have several processes
checking task numbers in a list none of them agreed on, and one shared journal
would have several appenders interleaving. The session identifier comes from
`ctx.sessionManager.getSessionId()`, part of the readonly session manager
surface every extension already receives.

The invariant this buys is stronger than a lock and needs no coordination:
**one writer per file, always.** A session writes its own journal and its own
state and nothing else. That holds for verdicts too -- a `/steward`
invocation in session A that verdicts a round from session B appends the
verdict to A's journal, not B's. Round identifiers are unique, so folding a
verdict onto its round is the same mechanical join whether the two records
share a file or not, and the reader has to fold either way.

**Decided: its own store, not the memory sink or MemPalace.** An append-only
audit log of verdicts and verbatim round summaries is a different concern from
semantic memory, and folding the two together would corrupt both -- a
correction journal must never be summarised, deduplicated or forgotten the way
a memory sink is meant to, and a memory sink must never carry verbatim
credentials in passing the way this journal's honesty requires it to.

Not in this repository, and not captured by `sync`. The journal quotes round
summaries verbatim, this repository is public, and a round summary is the most
likely place in the whole estate for a credential or a customer name to appear
in passing. It is machine state, not configuration.

### Two record types

Append-only is worth more than a single tidy row, because a verdict arrives
minutes or days after the round it judges, and rewriting a line in place is how
a log loses an entry to a crash or a second writer. So a verdict is its own
record, and a reader folds the two on `round_id`.

```json
{"type":"round","round_id":"019...","at":"2026-09-04T18:20:11Z","session_id":"019...","cwd":"/somewhere/maestro-pi-config","source":"tool_result","model":"qwen3-06b","role":"served","stage":"base","trigger":null,"summary_in":"...","operations":[{"check_task":3},{"note_decision":"..."}],"latency_ms":740}
{"type":"verdict","round_id":"019...","at":"2026-09-04T18:31:02Z","state":"corrected","operations":[{"flag_user":"..."}],"reason":"buried the blocker in a note"}
```

| Field | Why it is there |
| --- | --- |
| `round_id` | Joins a verdict to its round. Also the identifier the operator names. |
| `session_id`, `cwd` | Which pane produced it, and where it was working. Two panes on the same repository are two sessions, and a comparison that cannot tell them apart cannot be read. |
| `source` | Where the summary came from: `tool_result` for a dispatch that answered inside the turn, `completion_notice` for an async run whose report arrived later. The async and synchronous paths produce genuinely different inputs, and a column that hides that would make the model comparison meaningless. |
| `model` | The catalog entry that answered. The column the whole exercise exists to compare. |
| `role` | `served` for the proposal that reached disk, `shadow` for one recorded but not applied. |
| `stage`, `trigger` | `base`, `escalated`, or `escalation_unavailable`; and which rule sent it there. Makes a bad trigger visible as a pattern rather than an anecdote, and makes a fallback visible rather than silent. |
| `summary_in` | The exact input, as sent, after truncation. Without it a disputed verdict cannot be replayed against a different model. |
| `operations` | What was proposed, decoded, before validation. |
| `latency_ms` | The cost side of the comparison. |

**Deferred: `lane`.** This field was defined as "derived exactly as the lane
ledger derives it", against
`docs/superpowers/specs/2026-09-04-lane-ledger.md` -- a document that does not
exist in this repository. A field whose definition lives in an unwritten spec
is not a definition. `cwd` is recorded instead, because it is a fact the
extension already holds, and `lane` is added when the lane ledger spec lands
and says what a lane is. Duplicating a branch-derivation guess here would
guarantee the two disagree, which is the one outcome the shared derivation
existed to prevent.

A `verdict` record carries `state` (`accepted`, `corrected`, or `rejected`),
the corrected operations when the state is `corrected`, and a free-text
`reason`.

### How a verdict is captured

A slash command the extension registers, `/steward`, listing rounds with no
verdict and recording one. `registerCommand` is on `ExtensionAPI`
(`extensions/types.d.ts:946`) and pi-subagents already registers five commands
through it, so this needs no new binary and no second process.

It reads every session directory under the steward root, not just its own,
because the round worth verdicting is often one from a pane that has since
been closed. It writes only its own.

**Silence is not consent.** A round nobody verdicts stays `pending` for ever
and contributes nothing to the comparison. The temptation is to count an
un-corrected round as accepted, which would produce a large number that means
nothing: most rounds are never looked at, and a model that is never checked
would score identically to one that is always right. A small honest sample
beats a large false one.

Coverage is therefore itself a number worth reading. If after real use almost
nothing is verdicted, the journal has failed and the design needs a different
capture path, not a softer definition of acceptance.

## Two-stage escalation

The 0.6B answers by default. The 4B answers when the round looks like the case
the 0.6B got wrong.

This section describes the design in full, and it does not all switch on at
once. The trigger ships computed and recorded but not acted on, for the reason
given under "Not decided: which words are in each class" -- so on the first
day every round is served by the 0.6B, and the shadowing and fallback
behaviour below begins the day a measured vocabulary turns escalation on.

### The trigger

Computed by deterministic code **on the input**, before any model runs.

A **candidate** is a sentence in the round summary matching a flag vocabulary,
sorted into three classes: **severity** (the round may have touched something
dangerous), **blocker** (something is stopping the work), and **question**
(something is undecided).

Escalate when **either**:

- two or more candidates appear, from any class; or
- one candidate is from the severity class.

Otherwise the 0.6B answers alone.

Both clauses come straight from the observed failure. Two or more candidates is
the definition of competing priorities, which is the exact shape the 0.6B could
not order. A lone severity hit escalates because the cost is asymmetric: four
seconds against a missed security blocker is not a trade worth thinking about.

**Not decided: which words are in each class.** An earlier draft of this
document fixed the three lists here -- "security, vulnerability, credential,
secret, token" and the rest -- and that was a mistake worth naming, because
those lists are wrong in two ways that reading them cannot reveal.

They **over-fire on ordinary prose**. A round summary is written by an agent
reporting work, and this estate's agents discuss tokens, secret scanning and
security constantly while nothing is wrong: a summary reading "gitleaks found
no secrets and the token scan is clean" carries two severity hits and would
escalate every time. A trigger that fires on most rounds is not a trigger, it
is the always-the-4B alternative arriving by accident, without the argument
that alternative would have had to make.

They are **blind to negation**. Substring matching cannot tell "no credential
was exposed" from "a credential was exposed", and those are the two rounds
the whole design exists to tell apart.

So the vocabulary is not settled by writing a list down and believing it. It
is settled the way the model choice is: **against a fixture set of real round
summaries, with its fire rate measured before it is trusted.** Concretely,
before the trigger is enabled:

1. Collect round summaries from real sessions -- the journal produces them
   from its first day, since a `round` record carries `summary_in` whether or
   not it escalated.
2. Label each by hand as one that should escalate or one that should not.
   This is the operator's judgement and there is no substitute for it.
3. Report the fire rate of a candidate vocabulary over that set, both
   directions: how often it escalates a round that did not need it, and how
   often it misses one that did.
4. Ship a vocabulary only when both numbers are known and written into this
   document beside it.

Until that has been done, the extension runs with the trigger recorded and not
acted on: every round computes its candidates, journals them in `trigger`, and
is served by the 0.6B. That is the same data collection with none of the cost
of being wrong, and it is what makes step 3 possible at all.

**Decided: the vocabulary is a constant in the extension, not a governed
list.** That part stands. A governed list is a later change if the vocabulary
must vary across the estate; nothing yet shows it needs to (YAGNI). A constant
that has been measured is not the same thing as a constant that was guessed,
and only the second one was the problem.

### Why not ask the 0.6B to escalate itself

The obvious cheaper rule is to run the 0.6B first and escalate when it emits
more than one `flag_user`. It is wrong, and the bench says why. In the failure
it emitted **exactly one** `flag_user`, on the wrong item. A self-report is
blind in precisely the direction that matters: the model that cannot tell which
of two things is more important also cannot tell that it is in trouble.

### The alternatives, and why not

| Alternative | Why not |
| --- | --- |
| Self-reported escalation | Blind in the observed failure direction, above. |
| Always the 4B | ~4 s per round on rounds the bench shows the 0.6B answers in under one, against a model whose whole appeal is being cheap enough to run every round. Correct if the journal later shows the trigger under-fires; not correct as a starting point. The memory argument that used to sit in this row is gone: the 4B is resident either way, so it is held whether or not the steward calls it. |
| Both every round, serve the 4B | The previous row plus a wasted call. |
| Escalate on the operator's recent correction rate | Needs the journal to exist and hold data first. A good second-generation rule, an impossible first one. |
| No escalation, one model | Chooses between a model that is fast and sometimes wrong and one that is slow and usually right, before there is evidence to choose with. |

### Shadowing, so the journal can actually judge

An escalated round runs the 0.6B **first anyway**, records its proposal with
`role: "shadow"`, then runs the 4B and serves that.

Without this the journal is worthless for the comparison it exists for: the
0.6B would only ever be judged on easy rounds and the 4B only on hard ones, and
no verdict would ever compare them on the same input. The extra cost is one
sub-second call on the minority of rounds that escalate, which is a small price
for the only paired data the design can produce.

### When the escalation fails

The 4B can fail to answer: the endpoint refuses, the request times out, the
reply is not a 200. The earlier draft left this undefined, which meant the
behaviour on the highest-stakes rounds in the whole design -- the ones the
trigger picked out as dangerous -- was whatever the code happened to do.

**Decided: the shadow is promoted, never dropped.** The 0.6B has already
answered by the time the 4B is asked, so its proposal is on hand. On an
escalation failure the steward re-labels that record `role: "served"`, applies
it through the validator, and writes `stage: "escalation_unavailable"` with
the failure named. Dropping the round instead would mean the steward is
silently least useful exactly where it matters most, and the operator would
have no record that anything was missed.

Promotion is not a repair, and the record must not read like one. This is the
precise case the bench showed the 0.6B getting wrong, so a promoted round also
raises a notice to the operator -- deterministic code saying that an escalated
round was served by the small model, not a `flag_user` the model proposed --
and it goes to the front of the `/steward` queue. A promoted round with no
verdict is the least trustworthy row in the journal.

## Router integration: the steward must never cost the operator a model

The steward calls the model's dedicated endpoint on the local router:

- `http://127.0.0.1:8080/models/qwen3-06b/v1/chat/completions`
- `http://127.0.0.1:8080/models/qwen3-4b/v1/chat/completions`

Each with `response_format` carrying the schema above, `stream: false`, one
attempt, no retry.

### The decision this section reverses

An earlier draft of this document decided that **both entries must be
on-demand**, so that a router-wide idle window could free their memory between
rounds. That decision was wrong, and it was wrong in a way that would have
cost the operator real work. It is reversed here in full, along with
everything that rested on it.

The superseded spec had stated the guarantee correctly: a steward call never
triggers a model swap and never competes with the heavy models. The on-demand
decision quietly reversed that guarantee while arguing about memory, which is
how a non-negotiable constraint gets traded away -- not by being overruled but
by not being in the room.

Here is what it would have done, from the router's own admission code
(`maestro-llamacpp`, `src/admission.rs:148-208`), at the 30000 MiB budget the
catalog's residency note records:

- the operator is working with `qwen38`, held at an estimate of 24576 MiB and
  declared on-demand;
- the steward escalates and asks for `qwen3-4b` at the corrected estimate of
  7680 MiB;
- 24576 + 7680 = 32256, above the 30000 ceiling, so admission looks for
  eviction candidates: on-demand, not busy, not the entry being asked for;
- `qwen38` is the only candidate, and unloading it frees enough. The decision
  is `Unload(["qwen38"])`.

The steward would have evicted the 27B model the operator is working with, in
order to file a note about a round. And the timing makes it worse rather than
unlikely: `agent_settled` fires the moment the operator's model has finished
generating, which is precisely the moment it is not `busy` and is therefore
eligible for eviction. The window in which the steward runs is the window in
which `qwen38` is most evictable.

### The constraint, stated as a mechanism

**A steward call may only ever name a catalog entry declared `resident`.**

This is not a policy anyone has to remember. It is a property of the router as
built, in two lines of `src/admission.rs`:

- an entry that is already loaded returns `Decision::Fits` before any
  arithmetic is done at all (`src/admission.rs:157-159`), so a call for a
  resident entry cannot produce an unload or a refusal;
- a resident entry is never an eviction candidate, because the candidate
  filter admits only `Residency::OnDemand` (`src/admission.rs:182-187`), a
  rule the router has a test for.

So a steward call for a resident entry can neither evict a general model nor
be refused because a general model is loaded. Nothing swaps. Nothing waits for
a load. The guarantee holds by construction rather than by tuning a window.

### What that requires of the catalog

One line, in `maestro-llamacpp`: **`qwen3-06b` becomes `resident`.** It is
declared on-demand today at an estimate of 1024 MiB, and the bench measured it
holding about 1 GB, so the estimate is already honest. Held for ever, it
reserves 1024 MiB of the 30000 MiB budget, leaving 28976 MiB -- comfortably
above `qwen38`'s 24576 MiB, which therefore still fits beside it.

`qwen3-4b` is already declared `resident`, so the escalation stage needs no
catalog change to satisfy the rule.

The price is stated plainly: **about 1 GB of this machine's memory is held for
ever, whether or not the steward is used that day.** That is the cost of the
guarantee, it is the smallest form of it available, and it is worth paying.
The alternative on offer was a clerk that occasionally unloads the model the
operator is talking to.

### The `qwen3-4b` estimate, and what this design will not do about it

The earlier draft decided that the catalog's estimate for `qwen3-4b` must be
corrected up from 4096 MiB to 7680 MiB, because the bench measured about
7.25 GB on the processor at 32k context. The measurement stands and the
under-count is real -- but writing 7680 into the catalog has a consequence the
earlier draft did not follow through, and it is not this document's to impose.

`qwen3-4b` is resident. Residents reserve their estimate up front. At 7680,
the two residents would reserve 8704 MiB of 30000, leaving 21296 MiB -- less
than `qwen38` needs. Asked for `qwen38`, admission would find no eviction
candidate, because both residents are excluded, and return `Decision::Refuse`.
The estate's general-purpose 27B model would become unservable. That is not a
bug in the correction; it is the correction telling the truth about a machine
that is over-committed today and does not know it.

So this document records the finding and hands it to `maestro-llamacpp`, whose
catalog it is, rather than prescribing a number that would refuse the
operator's main model. The plausible resolutions -- a smaller declared context
for an entry whose largest caller sends a few hundred tokens, a budget that
distinguishes the video device from system memory, a larger budget -- are all
changes to that repository and each needs its own measurement.

**None of them changes anything here.** The steward's guarantee rests on
residency, not on the estimate: a resident entry is already loaded, so
`admit` returns before it reads the number. Whatever `maestro-llamacpp`
decides, the steward still cannot evict anything.

The deeper cause is worth naming for that repository: the budget is one number
covering two kinds of memory, and the small entries run with `n-gpu-layers=0`,
on the processor. So models that consume system memory are charged against a
ceiling sized for the video device, which is why a 1 GB clerk was ever in a
position to compete with a 24 GB model. A separate budget for
processor-hosted entries would remove the competition rather than manage it.
That is the principled fix and it is a router feature, not something this
design may assume.

### Idle unload does not apply here

The earlier draft configured `MAESTRO_IDLE_UNLOAD_SECONDS=300` and argued the
window at length. All of that is dropped, and the reasoning has to be dropped
with it rather than left standing as decoration.

Idle unloading only ever considers on-demand entries
(`src/admission.rs:182-187` and `src/idle.rs`). The steward's models are
resident, so no window value affects them, and the steward is no longer a
reason to configure one. Whether the estate wants idle unloading for other
reasons is a question for `maestro-llamacpp` and this document takes no
position on it.

The deployment claim went with it, and it deserves a correction rather than a
quiet deletion. The earlier draft said this design's dependency was that the
router's systemd user unit "carries
`Environment=MAESTRO_IDLE_UNLOAD_SECONDS=300` when it runs". **There is no
such unit.** `maestro-llamacpp` contains no `.service` file and no reference
to systemd anywhere in its sources, workflows or documentation; the superseded
spec placed the router's governance in that repository, not a unit. And with
the variable unset the router never idle-unloads at all -- `src/startup.rs:34`
prints "idle window: none set, so nothing is ever unloaded for sitting idle".
So the earlier argument rested on a mechanism that was neither deployed nor
written. Since the steward no longer needs it, nothing is proposed in its
place.

### Availability is not the steward's problem

The steward never starts the router. If the endpoint is unreachable or the
timeout expires, it writes a `round` record carrying `"error":
"router_unavailable"`, applies nothing, and the round proceeds untouched. Fail
open, every time: a clerk that can halt the work it is filing is worse than no
clerk.

Timeouts are the measured generation times with headroom -- 5 s for the 0.6B,
10 s for the 4B -- and they no longer have to cover a cold start, because a
resident entry has already paid it. A timeout on the 4B is an escalation
failure and promotes the shadow, per the section above.

## The integration point

**This was the crux, and the decision resting on the least direct evidence.**

A round summary has to come from somewhere, and the operations have to reach
something. Three ways in.

| Option | How the round arrives | Cost |
| --- | --- | --- |
| **A. Pi extension** on the main session's round boundary | The extension reads what the session already holds | Couples to pi's event surface; the summary has to be constructed, not received |
| **B. CLI at round end** | Whoever calls it passes the summary explicitly | Somebody has to call it. If that somebody is the orchestrator, the steward spends the turn it exists to save |
| **C. Hook** | pi invokes an external process at a lifecycle point | A third mechanism for what extensions already do here, against ADR-0001's grain |

### Decided: A, the extension

The extension listens on `agent_settled` in the main session. This repository
already chose that event and wrote down why -- pi may auto-retry or
auto-compact after `agent_end`, so `agent_end` does not mean finished. Two
extensions on this machine use it already.

Why A over B: the steward's entire justification is that it costs the
orchestrator nothing. B makes the orchestrator pay a tool call and the words to
describe the round, which is most of the cost the steward was meant to remove.
B remains the better answer if the transcript turns out to be an unreliable
source, because an explicit summary is a better input than a derived one -- so
this decision should be revisited the first time a journal entry shows a
`summary_in` that does not describe the round.

Why A over C: this repository has five extensions and no hooks, and ADR-0001
already routes lifecycle events through a shim into one process.

What follows is the part the earlier draft got wrong. `agent_settled` is the
right event; almost everything this document previously said about how to use
it was not.

### Only the main session

First line of the extension factory, before any handler is registered:

```ts
if (process.env.PI_SUBAGENT_CHILD === "1" || process.env.PI_STEWARD === "0") return;
```

Every subagent this estate dispatches is itself a pi session that loads the
same extensions, so without this guard the steward runs inside each child,
filing rounds about the child's own turns into a directory the operator will
never read, and asking the router to judge them. Four of this repository's
five extensions already carry exactly this line -- `maestro-guard.ts:7`,
`mempalace-autosave.ts:46`, `skill-router.ts:9`,
`mempalace-derive-relations.ts:342` -- with a second variable to switch the
extension off by hand. The steward follows the pattern rather than inventing
one.

### What a round is, and why it is not `ctx.isIdle()`

The earlier draft guarded the handler on `ctx.isIdle()` and called that "one
orchestration round". **That guard carries no information.** In
`agent-session.js`, `_emitAgentSettled()` sets `this._isAgentRunActive = false`
and only then awaits the extension emit (`agent-session.js:347-351`);
`isIdle` is defined as `!this._isAgentRunActive` (`agent-session.js:620-622`)
and `ctx.isIdle` is bound to it (`agent-session.js:2054`). Inside an
`agent_settled` handler it is true by construction, every time. It reads like
a check and it is a constant.

Worth naming rather than only fixing: `herdr-agent-state.ts:250` carries the
same guard, and it is equally uninformative there. The belief came from
somewhere, and the next reader will copy it again unless the reason it is
wrong is written down.

Nor does `agent_settled` mean "a round happened". It is emitted from the
`finally` of `_runAgentPrompt` (`agent-session.js:767-785`), so it fires once
per agent run whatever the run was: a typed question with no tool call, a
read, an abort part-way through. Filing all of those as rounds would fill the
journal with material the model has nothing to say about.

**A round is a settle at which there is something to judge.** Tracked from the
tool events, not from an idle flag:

- on `tool_call` where `event.toolName === "subagent"`, remember the
  `toolCallId`;
- on `tool_result` for a remembered id, keep the result;
- at `agent_settled`, a round exists if either a kept result carries a child's
  report, or the transcript holds a completion notice not yet filed (both
  below). Otherwise the handler clears its marks and returns, having done
  nothing.

An aborted turn leaves a remembered call with no result. Nothing is filed: a
record with no summary gives the model nothing to judge and the journal
nothing to compare. The marks are cleared at every settle, so nothing carries
into the next turn.

### Asynchronous dispatch, which is what this estate actually does

The earlier draft left it "unverified" whether `tool_result` carries the
child's report, and treated the answer as an implementation detail. It is not
a detail -- it decides what the steward can journal at all -- and for this
estate the answer is no.

pi-subagents dispatches asynchronously unless configured otherwise
(`src/extension/config.ts:233-234`: `asyncByDefault !== false`), and this
repository's `config/pi/settings.json` does not set it. An async dispatch
returns immediately with a receipt: content reading `Async: <agent> [<id>]`
and details carrying `results: []` alongside `asyncId` and `asyncDir`
(`src/runs/background/async-execution.ts:2077-2078`). The turn then settles
while the child is still working. There is no report at that settle, and
asking a model to judge a receipt is how a journal fills with confident
nonsense.

The two shapes are told apart from `event.details`, which pi passes through
for custom tools as an opaque value (`extensions/types.d.ts:766-769`):

| | Synchronous | Asynchronous |
| --- | --- | --- |
| `details.results` | non-empty | `[]` |
| `details.asyncId` | absent | the run identifier |
| `event.content` | the child's report | a receipt naming the run |
| Filed at this settle | yes, `source: "tool_result"` | no, nothing is filed |

**Decided: nothing is journalled at an async dispatch.** A round is filed when
there is a report to file, and for an async run that happens later.

When the child finishes, pi-subagents sends the completion into the parent
session as a custom message of type `subagent-notify`, carrying the child's
result (`src/runs/background/notify.ts:398-411`). Verified against real
session files on this machine: the entry is recorded as
`{"type":"custom_message","customType":"subagent-notify","content":...,"id":...}`,
and the content holds the report itself, not a pointer to it. That message is
sent with `triggerTurn`, so it usually starts a turn, and that turn settles.

So the async round's summary arrives at a **later** `agent_settled`, through
the transcript. At each settle the steward reads the session file reachable
from `ctx.sessionManager.getSessionFile()` -- the path `mempalace-autosave.ts`
already reads -- takes `subagent-notify` entries newer than the last entry id
it filed, and files one round each with `source: "completion_notice"`. The
high-water mark is the entry `id`, stored in `state.json`, so a notice is
filed exactly once even when no turn follows it.

**The dispatch and its completion are not joined.** `sendMessage` is called
with content and display only, no `details`, so the envelope carries no run
identifier a reader could match on; the identifier appears only inside prose
the steward would have to parse. Rather than parse it, the journal records the
completion on its own terms and pairing is left to a human with two timestamps
and an agent name. If pairing turns out to matter, the honest fix is a
`details` field on that message in pi-subagents, not a parser here.

The report can be long -- real notices on this machine run to several thousand
characters. `summary_in` is therefore truncated to a fixed budget and recorded
exactly as sent, so a disputed verdict replays against the same input. What
that budget should be, and whether the head or the tail of a report carries
the judgement, is the same kind of question as the flag vocabulary: settled
against a fixture set of real notices, not guessed here.

### Nothing waits for the steward

The "never blocking" non-goal was an aspiration the earlier design could not
have kept. Extension handlers are awaited one after another
(`extensions/runner.js:623-651`), and `_emitAgentSettled` awaits that emit
before releasing the session's idle wait (`agent-session.js:347-356`). A
handler that ran an escalated round inside the settle -- the 0.6B, then the
4B -- would have held the session for the duration of both, on the rounds most
likely to matter. That is the opposite of costing the round nothing.

**Decided: the handler captures, and never waits for a model.** At
`agent_settled` it does only synchronous, bounded work: read the kept tool
results, read the transcript tail, build the summary, compute the trigger.
Then it starts the model work without awaiting it and returns. The handler's
cost is a file read.

The pattern is the one `mempalace-autosave.ts` uses for the same event: hand
the work off, detach it, and return promptly rather than let a slow dependency
become the session's problem. The difference is that the steward's work is an
HTTP call in this process rather than a child process, so detaching means not
awaiting the promise, with its rejection handled.

When the reply lands -- typically under a second, possibly several turns
later -- the validator writes the `round` record and applies its operations to
`state.json`. If the session ends first, the round is lost and nothing is
written. That is the correct trade for a clerk: a lost note costs a line in a
ledger, and a held session costs the operator's time.

### Where the operations go, now that the work is detached

The earlier draft injected a rendering of `state.json` into the next round
through the `context` event. That cannot work as described, and the reason is
worth stating rather than the mechanism quietly changing: the state does not
exist when the settle ends. Injecting the result of work that has not started
into the turn it was derived from is not a thing that can be built.

**Decided: no context injection at all.** Two paths out, both matching what
the operations are for:

- **`flag_user` reaches the operator when it lands**, as a custom message
  through `pi.sendMessage` (`extensions/types.d.ts:971-974`), displayed, with
  `triggerTurn: false`. False is load-bearing: a steward that starts a turn
  has begun orchestrating, which is the first non-goal. pi-subagents already
  delivers background results into a settled session this way, so the seam is
  proven for work that finishes after its turn.
- **`check_task` and `note_decision` reach `state.json`**, and the operator
  reads them through `/steward`.

The rejected alternative is worth recording: injecting state on every LLM call
would spend context on every call, for a clerk whose justification is that it
costs the round nothing. If the orchestrator ever needs the task list in
context, it can be asked for -- that is a different feature, with a different
argument to make.

## Where it lives, and how it is governed

`config/pi/extensions/steward.ts`, beside the five extensions already there,
because that directory is the one `src/manifest.rs` mirrors into the live pi
extensions directory. A second source writing the same destination would make
`sync` capture the file back into a second place and report drift no sync could
resolve.

The cost, stated plainly: **`config/` is exempt from this repository's prose
gate.** The earlier draft listed three gates skipping that directory -- the
English test, markdownlint, a banned wording gate. Only the first exists here:
`tests/language.rs:31` skips `config`, and this repository runs no
markdownlint and no wording gate at all. The point survives the correction
intact, since the English gate is the one that would have caught something,
but a spec that names gates that do not exist is a spec whose other claims are
worth less. The steward is not third-party. Nothing about that exemption is
weakened by this design, but it now covers a file we wrote, and that is worth a
follow-up rather than a shrug. See the open questions.

Tests live at `extensions-tests/steward.test.mts`, tracked at the repository
root where the gates can see them, importing the extension the same way the
existing extension tests do: a fake `pi` object capturing the handlers, plus an
exported `__testing` surface for the pure functions. They run under
`node --test`, added as one line to `just check`. Standing up the full
TypeScript CI tier means a `package.json`, a lockfile, a formatter config and a
test runner in a repository that is otherwise Rust, which is a larger change
than this one and should be argued on its own.

## Its relation to the lane ledger

A sibling is planned -- another extension that watches orchestration, blocking
rather than recording. **Its spec is not written.**
`docs/superpowers/specs/2026-09-04-lane-ledger.md` does not exist in this
repository, and this document previously cited it as though it did, including
for the definition of a journal field. The comparison below is what the two
are meant to be; it is not a reading of a document anyone can open.

| | Lane ledger | Steward |
| --- | --- | --- |
| Watches | Dispatches on a lane | Rounds in the session |
| Acts by | Blocking, and demanding a written reason | Recording, and raising |
| Cost of being wrong | A blocked dispatch | A missed flag |
| May halt work | Yes, that is the point | Never |

Whether the ledger's state is ever absorbed into the steward's is a question
for the ledger's spec when it is written. Nothing here anticipates it, and the
shared lane derivation that was going to make a later fold mechanical is
deferred with the `lane` field itself, above.

## Test plan

Failing first, in the order they should be written. Each is a pure function or
a fake, so none needs a model to run.

1. **The grammar admits only the four operations.** Feed the schema a valid
   sample of each operation and a set of near misses -- an unknown key, two
   keys in one object, a string `check_task`, `noop: false`, an empty array,
   nine operations. Only the four shapes validate. Fails first because there is
   no schema.
2. **The validator refuses what the schema cannot express.** A `check_task`
   past the end of the state file, one already checked, a `noop` beside another
   operation. Each is rejected and journalled as rejected, and `state.json` is
   unchanged.
3. **A turn with no dispatch files nothing.** Emit `agent_settled` with no
   preceding `subagent` tool call and no unfiled notice. No journal record, no
   model call, `state.json` untouched. Fails first because the earlier design
   would have filed every turn. This is the test that pins the round
   delimiter, so it comes before the trigger tests.
4. **An async dispatch files nothing at its own settle.** A `tool_result`
   whose details carry `results: []` and an `asyncId`, then a settle: no
   record. Then a `subagent-notify` entry in a fake transcript, then a settle:
   one record with `source: "completion_notice"`. A second settle with the
   same transcript files nothing more, because the high-water mark holds.
5. **The handler returns before the model does.** With a fake endpoint that
   never answers, the `agent_settled` handler resolves promptly and does not
   reject. This is the "never blocking" non-goal as an assertion rather than a
   promise, and it fails against any implementation that awaits the call.
6. **Escalation fires on competing priorities.** A summary holding a security
   blocker beside routine progress escalates, with the trigger recorded. The
   exact bench summary is the fixture, so the case that produced this design is
   the case the test pins.
7. **The vocabulary does not fire on a clean round.** The fixture set of real
   round summaries labelled as not needing escalation produces no escalation.
   This test starts empty and grows, and it is what turns the vocabulary from
   a guess into a measurement; a fire rate is reported from it rather than
   asserted.
8. **A straightforward round stays on the 0.6B.** A single-item summary with no
   candidate terms does not escalate, and the journal names `qwen3-06b`.
9. **An escalated round journals both proposals.** One `shadow` record and one
   `served` record share a `round_id` and name different models.
10. **A failed escalation promotes the shadow.** With the 4B endpoint
    refusing, the 0.6B's proposal is applied, one record reads `stage:
    "escalation_unavailable"`, and the round is not dropped.
11. **The journal folds a verdict onto a round.** Append a round, append a
    verdict, read back one record with `state: "corrected"`. A round with no
    verdict reads back as `pending`, never as accepted. The fold works with
    the two records in different session files, because that is where a
    verdict from another pane lands.
12. **Two sessions do not share a file.** Two fake contexts reporting
    different session ids write two journals and two states, and a
    `check_task` in one leaves the other unchanged.
13. **An unreachable router costs the round nothing.** With the endpoint
    refusing connections, nothing throws, `state.json` is untouched, and the
    journal holds one record naming the error.

## What must happen elsewhere before this ships

One precondition, and one finding handed on.

1. **`qwen3-06b` becomes `resident` in the `maestro-llamacpp` catalog.** One
   line. Without it the steward has no entry it is allowed to call, because
   the resident-only rule is what makes the memory guarantee mechanical. This
   is a precondition, not a detail.
2. **The `qwen3-4b` estimate is under-counted, and correcting it refuses
   `qwen38`.** Recorded above with the arithmetic. It is a real problem in
   that repository's catalog, this design neither creates it nor depends on
   its resolution, and prescribing the number from here would break the
   operator's main model.

## Open questions for the operator

1. **The `config/` exemption over a file we wrote.** Accepting it is the
   surgical choice today. The follow-up -- moving authored extensions out of
   `config/` and leaving that directory to genuinely captured state -- touches
   five files and one manifest entry, and is a separate change if the operator
   wants it.
2. **About 1 GB held for ever, on a machine that is already tight.** That is
   the price of the memory guarantee and this design considers it worth
   paying. It is the operator's machine, so it is the operator's call, and it
   is the one cost here that cannot be reduced by writing better code.
3. **Whether escalation is worth having at all.** The trigger is unmeasured
   and starts recorded-but-not-acted-on, so the journal will say how often it
   would have fired before anything is spent on it. If the answer is rarely,
   the honest conclusion is one model and no escalation, and this document
   should lose several sections.

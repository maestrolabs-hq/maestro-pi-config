# The steward and its correction journal

Status: proposed design, not implemented. Supersedes Part 2 of
`docs/superpowers/specs/2026-09-03-agent-orchestration-and-steward.md`, which
recorded the steward as a sketch before any model had been measured. Part 1 of
that document, the routing matrix, is untouched.

The steward is a local model-driven clerk. It records each orchestration round
to a ledger and raises what needs the operator's attention. That is the whole
job.

## What the bench settled, and what it did not

Measured this session against the two candidate models on disk, both declared
in the router catalog of the `maestro-llamacpp` repository.

| | `qwen3-06b` (Q8, ~640 MB) | `qwen3-4b` (Q4) |
| --- | --- | --- |
| Load | ~1 s | ~6 s |
| Held while loaded | ~1 GB | ~7 GB at 32k context |
| Answer to a steward prompt | ~4 s | ~4 s |
| Answer with a `json_schema` grammar | ~0.75 s | ~4 s |
| Valid JSON without a grammar | yes | yes |
| Straightforward round | correct | correct |
| Round with competing priorities | **wrong** | correct |

Two findings carry this design.

**Form is free.** Both models emitted valid operations with no grammar at all,
and with a `json_schema` grammar the output is valid by construction. So a
schema is worth using -- it makes a class of failure impossible, and on the
0.6B it is also five times faster -- but nothing in this design may be built on
the belief that form was the hard part.

**Priority arbitration is where the small model fails.** Given a round holding
a security blocker beside routine progress, the 0.6B buried the blocker in a
`note_decision` and raised the routine item instead. The 4B ordered both rounds
correctly. The failure was not malformed, not refused, and not obviously wrong
from the output alone. It was a wrong judgement in valid clothes.

What the bench could not settle is which model to use in general. Two prompts
are two data points. That is what the correction journal exists to fix.

## Purpose

Round-by-round clerical upkeep, which today costs orchestrator turns and
context that should go to the work.

Each round the steward answers two questions:

1. What happened, in a form that can be read back later.
2. Is there anything here a human has to look at.

## Non-goals

- **Not the orchestrator.** It never dispatches, never re-dispatches, never
  chooses a model for anything but itself.
- **No engineering decisions.** It does not decide that a task exists, that a
  design is right, or that a failure is acceptable. It records and it raises.
- **Never blocking.** A steward that cannot reach its model, or that answers
  slowly, costs the round nothing. This separates it from the lane ledger,
  which is a gate and is supposed to block.
- **No write path beyond its own two files.** No tools, no shell, no arbitrary
  paths. The model proposes; deterministic code writes.
- **No training.** A fine-tune becomes a conversation only if the journal shows
  systematic error after real use.

## The operation vocabulary

Four operations, closed set.

| Operation | Meaning |
| --- | --- |
| `{"check_task": <int>}` | Mark task *n* in the current state file done. |
| `{"note_decision": "<text>"}` | Record something the round settled. |
| `{"flag_user": "<text>"}` | Raise one thing that needs a human. |
| `{"noop": true}` | The round changed nothing worth recording. |

`flag_user` is the only operation with a cost when it is wrong, in both
directions, so its semantics are narrow: **a risk, a blocker, something broken,
or an unresolved question.** Not progress. Not a summary. Not a plan. If a
competent operator reading it would not have to do anything, it is a
`note_decision`.

The earlier sketch used `add`, `complete`, `block`, `note`, `noop`. Two of
those are gone deliberately. `add` let the steward invent work, which is an
engineering decision and therefore not its to make -- a round that discovers
new work says so in a `note_decision` and the orchestrator decides whether it
is a task. `block` was `flag_user` under another name, and two words for one
idea is how a vocabulary rots.

### The schema

Sent as `response_format` on every call, so the router constrains decoding and
the reply cannot be malformed.

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["operations"],
  "properties": {
    "operations": {
      "type": "array",
      "minItems": 1,
      "maxItems": 8,
      "items": {
        "oneOf": [
          {
            "type": "object",
            "additionalProperties": false,
            "required": ["check_task"],
            "properties": { "check_task": { "type": "integer", "minimum": 1 } }
          },
          {
            "type": "object",
            "additionalProperties": false,
            "required": ["note_decision"],
            "properties": { "note_decision": { "type": "string", "maxLength": 280 } }
          },
          {
            "type": "object",
            "additionalProperties": false,
            "required": ["flag_user"],
            "properties": { "flag_user": { "type": "string", "maxLength": 280 } }
          },
          {
            "type": "object",
            "additionalProperties": false,
            "required": ["noop"],
            "properties": { "noop": { "type": "boolean", "const": true } }
          }
        ]
      }
    }
  }
}
```

The grammar guarantees shape, never sense. A deterministic validator sits
between the reply and the disk and refuses what the schema cannot express: a
`check_task` index outside the current list, an index already checked, a
`noop` arriving beside other operations. A refusal is journalled as a rejected
proposal, which is exactly the signal the journal exists to collect.

## The correction journal

The centrepiece. One line at a time, it turns a question nobody can answer from
a bench into a question that answers itself: **is the 0.6B good enough.**

### Storage

An append-only JSONL file, with the current task state beside it:

```text
<pi agent dir>/steward/journal.jsonl
<pi agent dir>/steward/state.json
```

The directory is derived at run time from `PI_AGENT_DIR`, falling back to the
pi directory under the home directory, the same derivation `src/manifest.rs`
already uses. Nothing here names a machine.

Not in this repository, and not captured by `sync`. The journal quotes round
summaries verbatim, this repository is public, and a round summary is the most
likely place in the whole estate for a credential or a customer name to appear
in passing. It is machine state, not configuration.

### Two record types

Append-only is worth more than a single tidy row, because a verdict arrives
minutes or days after the round it judges, and rewriting a line in place is how
a log loses an entry to a crash or a second writer. So a verdict is its own
record, and a reader folds the two on `round_id`.

```json
{"type":"round","round_id":"019...","at":"2026-09-04T18:20:11Z","session_id":"019...","lane":"maestro-pi-config@docs/steward-spec","model":"qwen3-06b","role":"served","escalated":false,"trigger":null,"summary_in":"...","operations":[{"check_task":3},{"note_decision":"..."}],"latency_ms":740}
{"type":"verdict","round_id":"019...","at":"2026-09-04T18:31:02Z","state":"corrected","operations":[{"flag_user":"..."}],"reason":"buried the blocker in a note"}
```

| Field | Why it is there |
| --- | --- |
| `round_id` | Joins a verdict to its round. Also the identifier the operator names. |
| `lane` | Repository and branch, derived exactly as the lane ledger derives it, so a later fold of the two records is mechanical rather than archaeological. |
| `model` | The catalog entry that answered. The column the whole exercise exists to compare. |
| `role` | `served` for the proposal that reached disk, `shadow` for one recorded but not applied. |
| `escalated`, `trigger` | Which stage answered, and which rule sent it there. Makes a bad trigger visible as a pattern rather than an anecdote. |
| `summary_in` | The exact input. Without it a disputed verdict cannot be replayed against a different model. |
| `operations` | What was proposed, decoded, before validation. |
| `latency_ms` | The cost side of the comparison. |

A `verdict` record carries `state` (`accepted`, `corrected`, or `rejected`),
the corrected operations when the state is `corrected`, and a free-text
`reason`.

### How a verdict is captured

A slash command the extension registers, `/steward`, listing rounds with no
verdict and recording one. `registerCommand` is the seam pi-subagents already
uses for its own commands, so this needs no new binary and no second process.

**Silence is not consent.** A round nobody verdicts stays `pending` for ever
and contributes nothing to the comparison. The temptation is to count an
un-corrected round as accepted, which would produce a large number that means
nothing: most rounds are never looked at, and a model that is never checked
would score identically to one that is always right. A small honest sample
beats a large false one.

Coverage is therefore itself a number worth reading. If after real use almost
nothing is verdicted, the journal has failed and the design needs a different
capture path, not a softer definition of acceptance.

## Two-stage escalation

The 0.6B answers by default. The 4B answers when the round looks like the case
the 0.6B got wrong.

### The trigger

Computed by deterministic code **on the input**, before any model runs.

A **candidate** is a sentence in the round summary matching the flag
vocabulary:

| Class | Terms |
| --- | --- |
| Severity | security, vulnerability, credential, secret, token, data loss, corruption |
| Blocker | blocked, blocker, fails, failing, broken, refused, cannot, regression |
| Question | unresolved, unclear, undecided, needs a decision, open question |

Escalate when **either**:

- two or more candidates appear, from any class; or
- one candidate is from the severity class.

Otherwise the 0.6B answers alone.

Both clauses come straight from the observed failure. Two or more candidates is
the definition of competing priorities, which is the exact shape the 0.6B could
not order. A lone severity hit escalates because the cost is asymmetric: four
seconds against a missed security blocker is not a trade worth thinking about.

### Why not ask the 0.6B to escalate itself

The obvious cheaper rule is to run the 0.6B first and escalate when it emits
more than one `flag_user`. It is wrong, and the bench says why. In the failure
it emitted **exactly one** `flag_user`, on the wrong item. A self-report is
blind in precisely the direction that matters: the model that cannot tell which
of two things is more important also cannot tell that it is in trouble.

### The alternatives, and why not

| Alternative | Why not |
| --- | --- |
| Self-reported escalation | Blind in the observed failure direction, above. |
| Always the 4B | ~7 GB held and ~4 s per round, on rounds the bench shows the 0.6B handles. Correct if the journal later shows the trigger under-fires; not correct as a starting point. |
| Both every round, serve the 4B | The previous row plus a wasted call. |
| Escalate on the operator's recent correction rate | Needs the journal to exist and hold data first. A good second-generation rule, an impossible first one. |
| No escalation, one model | Chooses between a model that is fast and sometimes wrong and one that is slow and usually right, before there is evidence to choose with. |

### Shadowing, so the journal can actually judge

An escalated round runs the 0.6B **first anyway**, records its proposal with
`role: "shadow"`, then runs the 4B and serves that.

Without this the journal is worthless for the comparison it exists for: the
0.6B would only ever be judged on easy rounds and the 4B only on hard ones, and
no verdict would ever compare them on the same input. The extra cost is one
sub-second call on the minority of rounds that escalate, which is a small price
for the only paired data the design can produce.

## Router integration and idle unload

The steward calls the model's dedicated endpoint on the local router:

- `http://127.0.0.1:8080/models/qwen3-06b/v1/chat/completions`
- `http://127.0.0.1:8080/models/qwen3-4b/v1/chat/completions`

Each with `response_format` carrying the schema above, `stream: false`, one
attempt, no retry. Timeouts are set from the measured numbers plus the load
cost the router may have to pay: 5 s for the 0.6B, 20 s for the 4B.

### Availability is not the steward's problem

The steward never starts the router. If the endpoint is unreachable or the
timeout expires, it writes a `round` record carrying `"error":
"router_unavailable"`, applies nothing, and the round proceeds untouched. Fail
open, every time: a clerk that can halt the work it is filing is worse than no
clerk.

### Idle unload, cabled into deployment

The router now supports `MAESTRO_IDLE_UNLOAD_SECONDS`, which unloads an
on-demand model nothing has asked for within the window and reloads it on the
next request. The steward is the caller that makes this worth configuring, so
it is configured here rather than as a separate effort.

**Window: 300 seconds.** One value has to serve both models, since the setting
is router-wide. During a working burst, rounds arrive minutes apart, so the
0.6B usually stays warm; when it does not, a reload costs about a second. An
escalation that already costs four seconds of generation can afford a
six-second reload. And overnight, nothing holds 7 GB. The router holds a model
for at most one and a half windows plus one sweep, so the real ceiling is about
seven and a half minutes.

**Both entries must be on-demand.** The catalog today declares `qwen3-4b` as
`resident`, and a resident is never a candidate for idle unload whatever the
window is -- so as things stand the escalation model would reserve its memory
permanently. Changing that is a one-line change in the `maestro-llamacpp`
catalog, in that repository, and it is a precondition for this design rather
than a detail of it.

**Deployment.** A user unit, `config/systemd/user/model-router.service`,
captured and provisioned exactly as `config/systemd/user/herdr.service`
already is, carrying `Environment=MAESTRO_IDLE_UNLOAD_SECONDS=300`. This
reopens a line in the superseded spec, which placed unit governance in the
router's own repository. The evidence for reopening it: that repository has no
provisioning mechanism, this one does, and this one already carries a user unit
for the same reason. Flagged below rather than assumed.

## The integration point

**This is the crux, and it is the part most likely to be wrong.**

A round summary has to come from somewhere, and the operations have to reach
something. Three ways in.

| Option | How the round arrives | Cost |
| --- | --- | --- |
| **A. Pi extension** on the main session's round boundary | The extension reads what the session already holds | Couples to pi's event surface; the summary has to be constructed, not received |
| **B. CLI at round end** | Whoever calls it passes the summary explicitly | Somebody has to call it. If that somebody is the orchestrator, the steward spends the turn it exists to save |
| **C. Hook** | pi invokes an external process at a lifecycle point | A third mechanism for what extensions already do here, against ADR-0001's grain |

### Proposed: A, the extension

`agent_settled` in the main session, guarded on `ctx.isIdle()`, which is one
orchestration round: the orchestrator dispatched, results came back, the turn
settled. This repository already chose that event and wrote down why -- pi may
auto-retry or auto-compact after `agent_end`, so `agent_end` does not mean
finished. Two extensions on this machine use it already.

The summary is built from the session transcript reachable through
`ctx.sessionManager.getSessionFile()`, bounded to what arrived since the
previous boundary. The pattern is proven: the memory autosave extension
already reads that path.

Operations reach disk through the deterministic validator into `state.json`,
and a compact rendering of that state is injected into the next round through
the `context` event, which is the seam `skill-router.ts` uses to add a message.
The superseded spec said `before_agent_start`; the `context` event is the one
proven in this repository to accept a modified message list.

Why A over B: the steward's entire justification is that it costs the
orchestrator nothing. B makes the orchestrator pay a tool call and the words to
describe the round, which is most of the cost the steward was meant to remove.
B remains the better answer if the transcript turns out to be an unreliable
source, because an explicit summary is a better input than a derived one -- so
this decision should be revisited the first time a journal entry shows a
`summary_in` that does not describe the round.

Why A over C: this repository has five extensions and no hooks, and ADR-0001
already routes lifecycle events through a shim into one process.

**What is not settled.** Whether `tool_result` carries the child's report text
is unverified. If it does, the summary for a dispatch-driven round is the
child's own report -- structured, authored to be read, and free -- and the
transcript reconstruction is not needed at all. That is an implementation-time
check against the installed runtime, and it would change the shape of the
input without changing this design. It is the first thing to test.

## Where it lives, and how it is governed

`config/pi/extensions/steward.ts`, beside the five extensions already there,
because that directory is the one `src/manifest.rs` mirrors into the live pi
extensions directory. A second source writing the same destination would make
`sync` capture the file back into a second place and report drift no sync could
resolve.

The cost, stated plainly: **`config/` is exempt from every prose gate this
estate runs** -- the English test skips it, markdownlint skips it, the banned
wording gate skips it -- because it is meant to hold captured third-party
state. The steward is not third-party. Nothing about that exemption is
weakened by this design, but it now covers a file we wrote, and that is worth a
follow-up rather than a shrug. See the open questions.

Tests live at `extensions-tests/steward.test.mts`, tracked at the repository
root where the gates can see them, importing the extension the same way the
existing extension tests do: a fake `pi` object capturing the handlers, plus an
exported `__testing` surface for the pure functions. They run under
`node --test`, added as one line to `just check`. Standing up the full
TypeScript CI tier means a `package.json`, a lockfile, a formatter config and a
test runner in a repository that is otherwise Rust, which is a larger change
than this one and should be argued on its own.

## Its relation to the lane ledger

`docs/superpowers/specs/2026-09-04-lane-ledger.md` describes a sibling: another
extension that watches orchestration. They are cousins and they stay separate.

| | Lane ledger | Steward |
| --- | --- | --- |
| Watches | Dispatches on a lane | Rounds in the session |
| Acts by | Blocking, and demanding a written reason | Recording, and raising |
| Cost of being wrong | A blocked dispatch | A missed flag |
| May halt work | Yes, that is the point | Never |

The ledger's own spec notes its state is a candidate for absorption into the
steward's. Not now, and nothing here anticipates it. The one concession is that
both derive a lane identically, so if the fold is ever made it is a merge of
two logs rather than a reconciliation of two vocabularies.

## Test plan

Failing first, in the order they should be written. Each is a pure function or
a fake, so none needs a model to run.

1. **The grammar admits only the four operations.** Feed the schema a valid
   sample of each operation and a set of near misses -- an unknown key, two
   keys in one object, a string `check_task`, `noop: false`, an empty array,
   nine operations. Only the four shapes validate. Fails first because there is
   no schema.
2. **The validator refuses what the schema cannot express.** A `check_task`
   past the end of the state file, one already checked, a `noop` beside another
   operation. Each is rejected and journalled as rejected, and `state.json` is
   unchanged.
3. **Escalation fires on competing priorities.** A summary holding a security
   blocker beside routine progress escalates, with the trigger recorded. The
   exact bench summary is the fixture, so the case that produced this design is
   the case the test pins.
4. **A straightforward round stays on the 0.6B.** A single-item summary with no
   candidate terms does not escalate, and the journal names `qwen3-06b`.
5. **An escalated round journals both proposals.** One `shadow` record and one
   `served` record share a `round_id` and name different models.
6. **The journal folds a verdict onto a round.** Append a round, append a
   verdict, read back one record with `state: "corrected"`. A round with no
   verdict reads back as `pending`, never as accepted.
7. **An unreachable router costs the round nothing.** With the endpoint
   refusing connections, the handler returns without throwing, `state.json` is
   untouched, and the journal holds one record naming the error.

## Open questions for the operator

1. **The integration point.** Proposed A, the extension on `agent_settled`,
   with B, an explicit CLI, as the named fallback. This is the decision the
   whole design hangs from, and the one where the proposal rests on the least
   evidence: whether a useful round summary can be reconstructed from a
   transcript has not been tried.
2. **Whether the router's unit belongs in this repository.** Proposed yes, at
   `config/systemd/user/model-router.service`. The superseded spec says unit
   governance for model serving lives in the router's own repository. That is
   an approved decision being reopened, and the operator should confirm the
   reopening rather than inherit it from a paragraph.
3. **Making `qwen3-4b` on-demand.** A change in another repository's catalog,
   and a precondition for the idle window to do anything for the escalation
   model. Does anything else depend on that entry being resident?
4. **The catalog's memory estimate for `qwen3-4b` reads 4096 MiB; the bench
   measured about 7 GB at 32k context.** If both numbers are right, the router's
   admission budget is optimistic for that entry rather than pessimistic, which
   is the wrong direction for a ceiling. Worth checking in the router's
   repository whether the estimate predates the context size.
5. **Where the journal lives.** Proposed its own store under the pi agent
   directory. The alternative is the estate's memory sink, which would make the
   journal queryable beside everything else recorded there -- at the price of
   coupling a local evaluation record to a consumer this estate deliberately
   keeps swappable, and of putting verbatim round summaries somewhere with a
   wider blast radius. Recommendation: its own store until the sink is asked
   for a second time.
6. **Whether the escalation trigger's vocabulary is governed or tuned.** As
   written it is a constant in the extension, changed by a commit. The
   alternative is a governed list that grows as misses are found. The second is
   better once there are misses to learn from and premature before then.
7. **The `config/` exemption over a file we wrote.** Accepting it is the
   surgical choice today. The follow-up -- moving authored extensions out of
   `config/` and leaving that directory to genuinely captured state -- touches
   five files and one manifest entry, and is a separate change if the operator
   wants it.
